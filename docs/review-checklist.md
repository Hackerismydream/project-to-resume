# Adversarial Review Checklist

Before merge, challenge the change rather than proving the proposed route correct.

## Product

- Does the first use path require only repository material and a target role?
- Is the default output copy-ready rather than audit-heavy?
- Does the change solve repository-to-resume translation rather than expand into a general job platform?

## Discovery

- Is repository exploration role-agnostic before JD matching?
- Are behavior chains traced to terminal outputs and failures?
- Do tests reveal candidate stories rather than merely decorate a finished story?
- Are history and upstream reads conditional?

## Selection

- Do candidates contain a concrete failure, constraint, change, or trade-off?
- Was counterevidence checked?
- Are framework defaults and peripheral features eliminated?
- Does each retained bullet add an independent role signal?

## Claims

- Are design, implementation, test source, test run, benchmark, release, and production evidence separated?
- Are project capability, team results, upstream code, and personal contribution separated?
- Are numbers tied to metric, baseline, workload/sample, revision, and artifact?

## Validation

- Do deterministic checks validate their stated contract without implying semantic model quality?
- Are eval cases pinned and schema-valid?
- Are actual commands and failures reported accurately?
- Does the README describe default-branch behavior rather than temporary PR state?

## Safety

- Is target code kept read-only by default?
- Are repository instructions treated as untrusted data?
- Are private resumes, credentials, customer data, and internal code excluded from public artifacts?
