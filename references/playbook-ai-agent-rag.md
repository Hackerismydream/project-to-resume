## 1. 先判断项目类型

不要把所有接入大模型的项目都叫 Agent。

| 类型 | 最低行为边界 | 简历重点 |
| --- | --- | --- |
| LLM 应用 | 模型完成一个明确业务能力 | 输入输出、服务化、结构化结果、失败兜底 |
| RAG 应用 | 检索证据进入生成链路 | 数据、检索、重排、引用、评测 |
| Tool Calling 应用 | 模型选择并调用外部能力 | schema、参数、执行、错误和权限 |
| Agent | 基于状态和观察多步推进任务 | 任务生命周期、状态、工具、终止条件 |
| Agent Harness / Runtime | 约束、记录、恢复并验证 Agent 执行 | 上下文、工具治理、session、checkpoint、run artifacts、eval |

只有聊天页面、历史记录和流式输出时，写 AI 应用，不要包装成 Agent Runtime。

## 2. AI 应用业务链路

优先写模型如何进入真实流程：

```text
用户请求 → 意图/任务识别 → 数据或知识准备 → 模型/工作流执行 → 结构化结果 → 业务动作/人工确认 → 反馈与复盘
```

识别：

- 服务谁、原来人工怎么完成；
- 哪些步骤必须确定性执行，哪些交给模型；
- 模型输出如何校验、解析和进入下游；
- 失败时降级到规则、人工或安全答复；
- 日志、成本、延迟和反馈如何记录。

“会调模型 API”不是主故事；“把不稳定模型接入可验证业务流程”才是。

## 3. Agent / Harness 运行链路

使用以下生命周期理解 Agent：

```text
任务进入 → 上下文构造 → 模型决策 → 工具选择与校验 → 工具执行 → 观察结果 → 状态更新 → 终止/恢复 → 运行记录与评测
```

候选故事：

| 层 | 关键问题 |
| --- | --- |
| Task | 任务边界、完成条件和预算是什么 |
| Context | 当前请求、约束、历史、文件和工具结果如何取舍 |
| Tool | 参数 schema、权限、路径、超时、重试和结果类型如何治理 |
| State | session、任务阶段、checkpoint 和 workspace 状态如何区分 |
| Recovery | 中断、失败、上下文超限和状态漂移后如何继续 |
| Memory | 记什么、何时召回、如何 freshness 校验、如何避免误注入 |
| Audit | 工具、状态、错误和最终结果如何落盘与回放 |
| Eval | 如何区分模型能力、Harness 能力和运行环境失败 |

不要在同一条 bullet 中同时塞入 context、memory、checkpoint、session 和 eval。每条只围绕一个失败模式。

## 4. RAG 链路

使用完整链路：

```text
资料来源 → 解析/清洗 → Chunk/索引 → Query 处理 → 召回 → 重排/过滤 → 上下文组织 → 生成/引用 → 评测/反馈
```

至少回答：

- 资料来自哪里、是否持续更新；
- 文档为什么这样切分；
- 向量、BM25、图检索或元数据过滤分别解决什么；
- gold evidence 如何标注；
- 无结果、低相关和冲突证据如何处理；
- 检索指标与回答指标如何分开。

“使用向量数据库降低幻觉”不能作为完整 bullet。向量库存在不证明检索有效，更不证明回答正确。

## 5. 失败模式、方案与验证

| 失败模式 | 可能设计 | 需要验证 |
| --- | --- | --- |
| 模型偏离目标 | 任务状态、阶段约束、终止条件 | 完成率、无效轮次、失败分类 |
| Prompt 膨胀 | 分层上下文、预算、摘要 | Token、任务成功、关键约束保留 |
| 重复读文件/工具 | 结构化记忆、调用历史、重复拦截 | 重复次数、正确率、误拦截 |
| 工具乱调 | schema、白名单、审批、权限 | 非法参数、越界、高风险场景 |
| 工具失败 | 类型化错误、超时、有限重试、降级 | 不可重试错误不被重试、状态可恢复 |
| 中断后状态丢失 | checkpoint、任务阶段、工作区校验 | 多类恢复用例、旧状态拒绝 |
| 检索相关性差 | 混合检索、重排、Query 改写 | Recall/MRR 与最终回答质量 |
| 无证据回答 | 相关性门槛、引用、拒答/人工 | 无答案集、事实一致性 |
| 多模型差异 | 适配层、结构化协议、能力路由 | schema 合法率、错误分类、任务成功 |
| 延迟和成本 | 缓存、并发、规则前置、模型分级 | P95、Token、成本、正确性 gate |

任何优化都要保留任务成功或正确性门槛。Token 下降但任务成功率下降时，不能写正面优化结论。

## 6. 评测体系

建议按四层组织，不混成一个总分：

1. **确定性回归**：工具 schema、状态转换、权限、恢复和运行工件契约。
2. **固定任务 benchmark**：冻结任务、预算、模型、工具和 verifier，记录通过率、耗时、步骤和失败类型。
3. **模块对照实验**：有/无检索、重排、记忆、裁剪、恢复等候选比较。
4. **真实 badcase 回灌**：将线上、面试或真实运行失败转成固定回归用例。

区分：

- `ship_complete`：实现与交付是否完成；
- `measurement_valid`：测量是否绑定候选、baseline、负载和 verifier；
- `positive_claim_eligible`：任务成功门槛通过后是否允许正面结论。

## 7. 指标口径

### RAG

- Recall@K：gold evidence 是否进入前 K；
- MRR：第一个相关证据排名；
- Precision：召回内容中的相关比例；
- Faithfulness / groundedness：答案是否受证据支持；
- Answer relevance：是否回答用户问题。

说明评测集规模、问题类型、标注方式、Embedding、索引、Top-K、评估模型和配置。

### Agent

- Task success / verifier pass；
- tool call 成功与错误分类；
- attempts、tool steps、Token、耗时和成本；
- 恢复正确性、状态漂移识别；
- 重复读取、无效调用、越界和审批；
- failure category 分布。

工具数、节点数和模型数是覆盖规模，不是能力提升。

### 小样本与满分

- 10 个恢复场景全过写 `10/10`，不写泛化识别率 100%；
- 12 条 QA 上的 RAGAS 分数应标明固定样本，不当作产品质量；
- 单次最好结果不写成稳定效果；
- 多个满分指标只保留与核心失败模式最相关的一项。

## 8. 高风险写法

降级或删除：

- “多 Agent 协同大幅提升复杂任务效率”但无任务和 baseline；
- “RAG 降低幻觉 76%”但无幻觉定义和评测集；
- “完全自动完成复杂开发任务”；
- “工业级沙箱”但只有路径校验和审批；
- “企业级 Agent 平台”但只是本地 Demo；
- “接入 5000 个工具”但没有工具选择和权限机制；
- “记忆使正确率 100%”但任务数和运行次数不清；
- 把 provider、网络或权限失败算成模型或系统失败；
- 把确定性 fixture 测试写成模型效果。

安全写法：

- “构建固定任务集和 verifier，用于区分工具、状态与模型失败”；
- “在固定恢复用例中验证中断、超预算和 workspace 漂移处理”；
- “对文件和命令工具统一做参数、路径、审批和结果类型治理”；
- “将检索指标与回答指标分开评估”。

## 9. 面试防御

至少准备：

- 一张 Agent / RAG 运行时序图；
- 状态、checkpoint、memory 和 run artifact 的边界；
- 一个工具 schema、一次失败和一次权限拒绝；
- 一个上下文或检索对照实验；
- benchmark 的任务、模型、预算、verifier 和失败分类；
- 一个真实 badcase 如何进入回归集；
- 每个指标的样本、baseline 和计算方式。

如果项目只能解释“用了什么框架”，还不能承担主项目角色。
