# 后端项目 Playbook

用于已经确定以后端为主线的项目。目标不是凑 Redis、MQ、Nginx 等关键词，而是找出：一次请求中的数据和状态如何流转，在并发、重复、超时和部分失败下如何收敛到正确终态。

## 1. 先建立业务模型

至少识别：

- **Actor**：用户、商家、运营、支付系统、库存系统或下游服务；
- **Aggregate**：活动、资格、库存、订单、支付、退款、消息、任务等核心对象；
- **State**：谁能推动状态变化，哪些转移非法，哪些是终态；
- **Boundary**：本地事务、缓存、消息、服务和团队边界；
- **Invariant**：一人一单、库存不为负、订单只结算一次、任务只产生一次业务效果等约束；
- **Reverse Flow**：取消、超时、退款、回滚、补偿、对账和人工介入如何收敛。

内部把主线写成：

```text
当前状态 → 触发事件 → 前置校验 → 数据写入/外部副作用 → 下一状态 → 失败/重试行为
```

学生项目最有价值的不是功能数量，而是一条完整正常链路、一条异常/逆向链路，以及守住它们的不变量。

## 2. 只有仓库时的定向阅读

沿请求链路读，不按目录穷举：

1. API、Controller、应用服务：请求从哪里进入，返回什么；
2. 表结构、领域对象、状态字段：事实和状态存在哪里；
3. 事务、锁、唯一约束、幂等键：原子边界在哪里；
4. Redis、缓存和库存脚本：哪些状态被加速、预占或短暂复制；
5. MQ producer/consumer：哪些动作移出同步链路；
6. 补偿、对账、定时任务、死信和人工介入：失败后如何恢复；
7. 测试、压测、日志、指标和告警：哪些行为实际被验证或观察。

每个发现整理为：

```text
业务对象 | 触发 | 不变量 | 机制 | 失败窗口 | 恢复 | 验证 | 个人边界
```

再交给通用故事排序器，不能每发现一个组件就生成一条 bullet。

## 3. 常见业务链路

### 交易、秒杀和拼团

```text
活动校验 → 用户资格 → 库存预占 → 订单创建 → 支付回调
→ 成交/成团 → 超时释放 → 取消/退款补偿
```

重点确认：库存事实源、预占/确认/释放、一人一单、重复支付回调、消息重投、超时订单和退款恢复。

### 优惠券与营销资格

```text
规则配置 → 资格判断 → 券领取/预占 → 使用核销 → 过期/撤销 → 额度恢复
```

重点确认：用户、活动和券批次的约束；规则版本；重复领取；核销与订单状态；过期扫描；撤销后的逆向变化。

### 短链与读多写少系统

```text
创建短链 → 唯一码生成/冲突处理 → 映射写入 → 访问跳转
→ 异步采集 → 聚合统计 → 失效/迁移
```

重点确认：短码冲突、无效请求、热点 Key、缓存失效、跳转与统计解耦、分片键和查询路由。

### 任务、调度与后台系统

```text
任务提交 → 调度/抢占 → 执行 → 心跳/超时 → 重试或取消
→ 结果产出 → 状态展示 → 告警/人工介入
```

重点确认：幂等键、任务归属、并发领取、重试条件、僵尸任务、结果写入、失败分类和状态口径。

### 本地生活、内容与社交

GEO、ZSet、Set、Bitmap、HyperLogLog 分别关联附近检索、排序、关系计算、签到和 UV 估算。只保留能解释数据模型、查询行为和边界的 1–2 个故事，不写数据结构清单。

## 4. 事务与状态

先回答：

- 一个本地事务包含哪些数据库写入；
- 哪些缓存、消息和外部调用不在事务中；
- 回滚时已经产生的外部副作用如何处理；
- 重复请求、重复回调或重试是否再次推进状态；
- 失败后系统靠重试、补偿、对账还是人工收敛；
- 非法状态转移如何被拒绝。

安全表达：

> 将订单写入与消息记录置于同一本地事务，提交后异步投递，并通过状态校验和补偿任务处理投递失败。

不能仅凭 `@Transactional` 写“保证分布式强一致”，也不能只因存在状态字段就写“设计完整状态机”。状态机至少要有合法转移、幂等推进、异常/逆向路径和终态判断。

## 5. 库存、资格与并发

必须确定：

- 数据库还是 Redis 是库存事实源；
- 库存何时预占、确认、释放和对账；
- 同一请求如何避免重复预占、下单和释放；
- Lua、数据库条件更新、悲观/乐观锁、唯一索引分别守哪条不变量；
- Redis 预占成功而订单落库失败、支付超时或退款时如何恢复；
- 热点冲突和重试成本是否会反噬吞吐。

Redis Lua 只保证脚本内操作原子，不自动覆盖 Redis、数据库和 MQ 的跨组件一致性。唯一索引能兜底重复写入，但仍需定义冲突后的业务返回和已产生副作用。

安全表达：

> 通过 Lua 原子完成资格与库存预占校验，并以订单唯一约束和状态校验兜底重复请求；失败路径由补偿任务释放预占资源。

“零超卖、绝对一致、重复率为 0”必须带并发负载、样本、检查方式和结果。

## 6. 缓存

先画出读写路径：

```text
请求 → 缓存命中/未命中 → 回源 → 重建 → 返回
写请求 → 事实源更新 → 缓存更新/删除 → 并发读窗口
```

至少说明：

- 缓存对象、Key、TTL 和事实源；
- Cache Aside 或其他策略的读写顺序；
- 不存在对象、热点 Key、集中失效、陈旧数据分别怎么处理；
- 缓存重建失败、并发更新和回源压力如何限制；
- 哪些数据允许短暂不一致，哪些必须读事实源。

机制与问题要一一对应：

| 问题 | 候选设计 | 必须说明的代价 |
| --- | --- | --- |
| 穿透 | 空值缓存、布隆过滤器 | 空值过期、误判、更新同步 |
| 击穿 | 互斥重建、逻辑过期、singleflight | 等待、陈旧数据、实现复杂度 |
| 雪崩 | 随机 TTL、分批预热、限流降级 | 预热成本、内存、降级体验 |
| 热点 Key | 本地缓存、拆分、请求合并 | 一致性、失效广播、分片规则 |
| 写后陈旧 | 删除/更新顺序、延迟双删、版本号 | 窗口仍存在、补偿复杂度 |

没有命中率和负载数据时，只写源码可见的确定性行为，例如“缓存命中时跳过数据库查询”“热点失效时合并同一 Key 的并发重建请求”；可以写“用于控制穿透/击穿风险”，不能把设计目的写成已测得的整体效果，更不能写“显著提升性能”或“保证强一致”。

## 7. MQ 与跨组件一致性

先说明 MQ 异步处理什么，以及为什么不能留在同步主链路。随后检查：

- 业务提交后消息如何可靠产生；
- producer 发送失败、超时或重复时怎么处理；
- consumer 的幂等键、状态校验和副作用边界；
- 重试、乱序、死信和积压如何处理；
- 补偿再次失败时如何告警、对账或人工介入。

至少覆盖这些失败窗口：

```text
数据库提交前失败
数据库已提交、消息未发出
消息已处理、ACK 丢失
重复或乱序消费
补偿任务再次失败
```

本地消息表 / Outbox、幂等消费、有限重试和补偿可以支撑“状态最终收敛”的故事，但不能自动推出“消息绝不丢失、Exactly Once、分布式强一致”。异步化减少同步等待，不等于总工作量或成本下降。

## 8. 数据库与性能

性能故事必须从瓶颈开始：

```text
场景与热点路径 → baseline → 数据量/请求分布/并发 → 环境
→ 观测到的瓶颈 → 改动 → QPS/尾延迟/错误率/资源 → 正确性 gate → 边界
```

### 慢查询

说明过滤、排序、分页和关联方式；结合执行计划判断扫描行数、回表、临时表、filesort、锁等待和索引选择。索引存在不等于查询变快，联合索引也必须解释字段顺序和写放大。

### 分库分表

只有能说明分片对象、分片键、路由、全局唯一 ID、跨分片查询、扩容迁移和热点问题时才作为主故事。仅接入中间件不能写“解决海量数据”。

### 异步、批量与预聚合

说明工作从哪条主链路移到哪里、何时可见、失败如何补偿，以及写放大、陈旧数据或队列积压代价。

没有完整压测口径时，写系统行为，例如“将访问统计移出同步跳转链路，减少主请求中的阻塞点”，不要补 QPS、P95 或“数倍提升”。

## 9. 稳定性与可观测性

限流、熔断、降级和重试不能作为四个并列名词。每个机制必须绑定：触发信号、保护对象、阈值来源、恢复条件和用户/数据后果。

- 超时预算要沿调用链分配；
- 重试只用于可重试错误，并考虑幂等和重试风暴；
- 熔断要说明打开、半开和恢复行为；
- 降级要说明丢弃或返回什么，是否影响正确性；
- 限流要说明维度、算法、突发处理和拒绝结果。

可观测性故事要说明日志、指标或 trace 如何缩小问题范围，而不是只写“接入 Prometheus”。常见关联：request_id / order_id、状态转移、队列积压、补偿失败、慢 SQL、缓存回源和下游错误分布。

## 10. 验证层级与指标口径

正确性先于性能。按项目实际拥有的层级选择：

1. 正常请求和合法状态转移；
2. 重复请求、重复回调和重复消费；
3. 并发库存或并发更新；
4. 数据库回滚和部分写入；
5. 缓存未命中、过期和并发重建；
6. 消息发送失败、重投、乱序和积压；
7. 补偿重跑、对账差异和人工介入；
8. 固定负载下的吞吐、P95/P99、错误率、资源和恢复时间。

压测至少保存：机器和实例数、依赖版本、数据量和 Key 分布、读写比、并发、持续时间、预热、baseline、正确性检查、原始脚本与报告。

措辞随证据层级变化：

| 已知事实 | 可写措辞 |
| --- | --- |
| 只有实现 | “实现……用于处理/控制……风险”；职责明确时才写个人“设计” |
| 仓库有测试源码，未见运行结果 | “编写/补充……测试 case” |
| 测试实际运行 | 准确写通过用例和条件 |
| 固定负载压测 | 带 baseline、负载、环境和指标写结果 |
| 用户明确提供真实线上结果 | 带业务范围与时间窗口写线上结果 |

测试文件存在不等于测试通过；配置数字不等于运行结果；部署代码不等于真实生产使用。

## 11. 真实排障闭环

只在材料明确表明真实发生时使用：

```text
触发 → 用户/系统症状 → 影响范围 → 监控/日志 → 假设
→ 复现 → 根因 → 修复 → 回滚/保护 → 回归 → 防复发
```

简历保留症状、根因、关键修复和验证；完整时间线放面试防御卡。测试中模拟 broker 不可用、缓存过期或数据库回滚只能写“故障注入/异常测试”，不能包装成线上事故。

## 12. 高风险措辞与防御材料

降级或删除：千万级、百万并发、企业级、高可用、生产级、彻底解决超卖、绝对一致、零消息丢失、没有口径的数倍提升。

常见安全降级：

- “支撑高并发” → “针对并发下的重复请求与库存竞态设计控制”；
- “保证一致性” → “通过幂等、补偿和状态校验使异常链路收敛”；
- “吞吐提升 6 倍” → “将非关键统计写入从请求主链路异步拆出”。

面试至少准备：业务状态机、核心请求时序、异常/补偿链路、关键表与索引、Redis Key 或消息体、一个并发正确性测试、一个排障或压测案例、每个关键方案的替代方案与不采用原因。

如果 bullet 无法落到其中至少一项，删除或降级。
