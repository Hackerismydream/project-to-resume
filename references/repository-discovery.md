# 陌生仓库探索与行为链路追踪

本文件负责 repository-first 流程的前半程：先建立搜索空间，再从真实系统行为中发现候选故事。它不负责最终简历句式，也不输出完整仓库审计报告。

## 1. 目标与反目标

目标：

- 在不依赖目标岗位关键词的情况下，快速理解仓库“接收什么、维护什么状态、做出什么决策、产生什么副作用、怎样结束或恢复”；
- 选择 2–4 条最可能承载工程价值的行为链路；
- 用测试、必要的历史和 upstream 差异发现失败边界与设计变化；
- 为 Story Hypothesis 提供足够证据和反证。

反目标：

- 不做逐目录、逐类、逐函数的全量讲解；
- 不把 README 复述、技术栈清单、Controller/Service/DAO 列表当项目故事；
- 不因 JD 写了 Redis、Kafka、RAG、Agent 就只搜索这些词；
- 不默认联网抓取完整 PR、issue 和 history；
- 不运行不可信项目代码来“证明”仓库能力。

## 2. 先固定仓库身份

在任何深读前记录：

```text
repository path / URL
HEAD 或固定 commit
branch
working tree dirty state
remote default branch
fork / upstream
观察范围与观察时间
```

必须区分：

- 当前工作树与 HEAD；
- 当前分支与远端默认分支；
- 当前实现与历史实验；
- 源码与发布产物；
- fork 当前能力与 upstream 原有能力。

若用户提供的是公开 URL 而不是本地工作区，个人归属保持未知；仓库作者、提交者、维护者都不自动等于候选人本人。

## 3. Repository Map：轻量广度扫描

Repository Map 至少覆盖以下字段。未知可以保留，不为完整而猜测。

| 维度 | 要寻找的事实 | 常见锚点 |
| --- | --- | --- |
| 身份 | commit、branch、dirty、fork、upstream | Git 元数据、仓库页面 |
| 目录与语言 | 顶层结构、主要语言、单体/多包 | tree、manifest、构建文件 |
| 构建与启动 | 如何构建、启动、安装、发布 | pom、gradle、pyproject、package、Makefile、CI |
| 执行面 | API、CLI、worker、cron、consumer、UI、daemon、hook | 路由、命令注册、入口函数、工作流 |
| 核心对象 | 实体、任务、会话、订单、文档、索引、状态机 | model、schema、migration、enum |
| 状态与数据 | 持久化位置、状态迁移、唯一性、版本 | DB schema、repository、store、checkpoint |
| 输入 | 请求、事件、文件、消息、模型输出、用户动作 | DTO、schema、parser、handler |
| 输出与副作用 | DB 写入、消息、文件、网络调用、外部 CLI、可见响应 | adapter、client、publisher、writer |
| 失败与恢复 | 重试、补偿、幂等、回滚、拒绝、超时、取消 | exception、retry、recovery、cleanup |
| 测试 | 单元、集成、故障注入、回归、契约、快照 | tests、fixtures、assertions |
| 测量与发布 | benchmark、profile、release、migration、changelog | scripts、reports、tags、docs |
| 历史材料 | commit、PR、issue、upstream diff 是否可用 | git log、remote、链接 |
| 未知项 | 会改变故事、归属或 Claim 的缺口 | 显式记录 |

Repository Map 的完成标志不是“所有文件都看过”，而是能够画出主要执行面和核心状态之间的关系，并知道下一步应追踪哪些行为。

## 4. 如何识别执行面

不要只找 Web Controller。不同项目的入口可能是：

- Java / 后端：HTTP/RPC、消息消费、定时任务、支付回调、管理命令；
- Agent Runtime：Turn/Run 入口、模型调用、Tool Call、Gateway、Cron、Channel、Subagent；
- RAG：文档导入、增量更新、查询、召回、重排、引用回答、删除传播；
- CLI：命令解析、配置加载、执行器、退出码、文件或终端输出；
- 数据流水线：Source、transform、checkpoint、sink、重跑和迟到数据；
- 调度系统：提交、排队、claim、lease、heartbeat、执行、终态；
- 前端状态：用户事件、state transition、网络请求、乐观更新、回滚；
- 基础设施：配置输入、资源变更、探针、故障隔离、恢复和审计。

识别入口后，继续问：它触发了哪个核心对象的状态变化？最终谁能看到什么结果？

## 5. 从 Map 选择 2–4 条行为链路

优先选择满足更多以下特征的链路：

- 从真实入口进入核心对象，而不是文档或管理边缘；
- 包含关键状态迁移或资源所有权变化；
- 有外部副作用，重复执行会产生后果；
- 存在失败、并发、权限、恢复、版本或兼容性约束；
- 有测试、迁移、历史变化或运行材料可交叉检查；
- 能解释项目为何不仅是框架样例。

不要在此阶段按目标岗位选链路。岗位只在候选池形成后决定哪些故事进入成稿。

## 6. 行为链路模板

每条链路按下面的顺序还原：

```text
入口
→ 输入校验
→ 核心数据或状态
→ 关键决策
→ 外部副作用
→ 终态或可见输出
→ 异常与恢复
→ 测试或验证
```

### 入口

谁或什么触发行为？HTTP 请求、消息、命令、定时器、模型输出、文件变化、用户交互都可能是入口。

### 输入校验

哪些输入在进入核心状态前被拒绝、规范化或补全？关注权限、schema、版本、路径、幂等键、参数组合和前置状态。

### 核心数据或状态

哪个对象承载过程？状态是显式枚举、数据库行、checkpoint、队列记录，还是只隐含在调用栈中？谁拥有写权限？

### 关键决策

项目在哪些分支做出工程判断？例如是否重试、是否回滚、是否拒答、是否复用旧结果、是否异步、是否升级到人工。

### 外部副作用

是否写数据库、发消息、调用支付、修改文件、启动进程、写索引或向模型发送上下文？副作用如何避免重复或越权？

### 终态或可见输出

系统怎样宣布完成、失败、取消或部分成功？用户、下游或运维能看到什么？中间状态是否能够收敛？

### 异常与恢复

读取超时、重复、部分成功、中断、过期状态、版本漂移、无结果、权限失败与清理路径。没有异常分支的链路通常还没有读深。

### 测试或验证

寻找对应的断言、故障注入和运行材料。明确“测试源码存在”和“指定 revision 实际运行通过”的区别。

## 7. 让测试反向指向故事

测试不是最后才读的证明附件。它可以暴露项目真正担心的问题。

优先观察：

- 测试名称中反复出现的 failure / recovery / duplicate / stale / permission / timeout / rollback；
- fixture 构造了哪些不正常状态；
- 断言关注返回值、终态、唯一性、持久化、清理还是可见证据；
- 故障注入发生在主链路哪个阶段；
- 回归测试是否暗示过去发生过的缺陷；
- 测试是否覆盖框架默认行为之外的项目设计。

测试能够支持的发现：

- 重要不变量；
- 恢复和补偿路径；
- 权限与安全边界；
- 兼容性约束；
- 历史故障线索；
- 哪些行为值得形成 Story Hypothesis。

证据边界：

- 测试文件存在：只能说“编写/包含某类测试场景”；
- 有可归属的运行记录：可以说“在该 revision 和环境下指定场景通过”；
- 两者都不能直接说“生产稳定”“高可用”或“成功率提升”。

## 8. 条件式读取 history、PR、issue 与 upstream

只有出现以下触发器时才扩大范围：

| 触发器 | 需要历史材料回答的问题 |
| --- | --- |
| 当前结构看不出动机 | 旧方案是什么，为什么替换 |
| fork / 二次开发 | upstream 已有什么，当前仓库新增什么 |
| README 与源码不一致 | 哪个 revision 或发布状态更可信 |
| 回归测试突出某故障 | 是否有对应缺陷、修复或迁移 |
| 用户提到重构/迁移/性能变化 | 比较对象和变化边界是什么 |
| 候选依赖“从 A 到 B” | A、B、commit 和验证是否同一口径 |

优先使用本地 Git 信息；只有必要且已获准时再访问远端。不要为了“研究充分”抓完整历史。

历史材料可以发现：

- 隐式状态变为显式状态机；
- 同步主链路拆为异步与补偿；
- 恢复、幂等、权限、兼容性或数据迁移；
- upstream delta；
- 过期 benchmark 与当前代码不一致。

历史材料同样受 Claim 分层约束：commit message 是设计/变更线索，不自动证明效果。

## 9. 主路径与外围能力

把候选内容分成三层：

1. **核心行为**：缺失后项目无法完成主要任务或状态无法收敛；
2. **质量与治理**：控制核心行为的失败、权限、恢复、验证和可解释性；
3. **外围便利**：脚手架、展示页、普通 CRUD、简单配置、包装命令。

外围能力只有在体现独立工程判断、对目标岗位有新增信号且有证据时才占用 bullet。模块体积大、名词高级或 README 篇幅长，都不能替代核心性。

## 10. 阅读停止条件

满足以下条件后停止：

- 主要执行面和核心状态已进入 Map；
- 2–4 条核心链路能够从入口讲到终态与恢复；
- 测试分布已用于发现失败边界；
- 强候选已有源码/测试锚点、反证和未知项；
- history/upstream 的触发条件不存在，或已回答关键差异；
- 新读文件只重复现有机制或补充不能进入简历的外围细节；
- 剩余未知不会改变定位、归属、数字或 Claim 上限。

若仍有会改变成稿的未知，转为最多三个具体问题，不进行无边界扫描。

## 11. 常见误判

- **按目录写故事**：列 Controller、Service、DAO，而没有状态和终态。
- **README 即事实**：把定位、路线图或宣传语写成已实现能力。
- **组件即亮点**：看到 Redis、Kafka、Vector DB、Checkpoint 就直接生成 bullet。
- **测试即通过**：只看测试文件便使用“验证通过”。
- **配置即结果**：把 timeout、retry、Top-K、TTL 写成性能或质量提升。
- **history 默认全扫**：阅读成本失控，却没有改变候选排序。
- **JD 提前收窄**：只寻找岗位关键词，漏掉真正差异化的故障和状态故事。
- **fork 冒领**：把 upstream 能力全部写成本人实现。
- **过度审计**：把内部 Map、SHA 和证据表当默认用户产物。
