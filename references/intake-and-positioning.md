# 输入路由、岗位定位与项目选择

本文件只在仓库的岗位无关发现完成后，负责目标岗位、项目组合与 JD 排序。它不能反过来决定 Repository Map 应该寻找什么。

## 目录

1. 输入清点
2. 三种输入路线

5. 项目评分

8. 完成标准

## 1. 输入清点

先在内部建立材料清单，不要求用户重新整理已经提供的内容。

| 材料 | 主要用途 | 不能单独证明 |
| --- | --- | --- |
| 项目仓库 | 系统边界、执行面、状态、实现机制、测试与文档 | 个人归属、测试已运行、上线和业务效果 |
| 现有简历 | 岗位意向、个人职责、用户陈述、已有数字 | 仓库当前实现、数字已核验 |
| 用户补充说明 | 业务背景、个人边界、真实故障、投递目标 | 外部可验证性 |
| JD | 发现完成后的选材、排序和岗位语言 | 新技术、新职责、新结果 |
| benchmark / 报告 | 固定 revision 和条件下的有界结果 | 当前发布或生产效果 |
| offer / 面试反馈 | 岗位匹配和追问风险 | 项目技术事实 |

记录缺失项，但只在缺失会改变成品时追问。

## 2. 三种输入路线

### 有仓库

1. 先按 [repository-discovery.md](repository-discovery.md) 固定身份并建立岗位无关的 Repository Map。
2. 追踪 2–4 条行为链路，让测试参与发现，按条件读取 history 或 upstream。
3. 按 [story-selection.md](story-selection.md) 形成候选、检查反证并完成首轮竞争。
4. 之后才使用本文件确定岗位画像、项目组合与 JD 排序。
5. 用户在简历语境中提供本地仓库时，可暂按候选人项目处理，对可见实现使用普通个人动词；公开第三方 URL、团队项目或上游项目仍需区分贡献边界。
6. 没有真实用户或业务时，使用任务场景和系统失败模式，不虚构业务价值。

### 只有简历或项目说明

1. 保留用户明确陈述的业务、职责、技术和结果。
2. 找出岗位错位、项目重叠、技术报菜名、业务对象缺失、数字无口径和职责过大的句子。
3. 不补材料中没有的实现机制；原句只有技术名词时，把名词还原成已知行为，不反向脑补完整架构。
4. 含糊数字先改成无数字版本；只问一个可以把该数字补回的问题。
5. 先交付完整替换稿，不做逐句批注，除非用户要求审稿。

这条兼容路线保留现有简历优化能力，但不是 repository-first 产品的核心路径。

### 简历 + 仓库

1. 仓库先独立完成 Repository Map、行为链路和候选发现。
2. 简历和用户说明补充业务背景、个人角色和原始数字，而不替换仓库事实。
3. 建立逐条映射：`原简历 claim → 仓库补充 → 冲突/缺口 → 新措辞`。
4. 简历强于仓库时，不直接判用户为假；缩小措辞并提出具体确认问题。
5. 仓库有亮点但简历未体现时，只有能与用户职责相连才写入个人 bullet。

## 3. 岗位介入时机

可以在开始时记录目标岗位和 JD，但在以下条件满足前不得用它缩窄仓库搜索：

- Repository Map 已覆盖主要执行面、核心对象、状态、输入输出和测试分布；
- 已追踪 2–4 条从入口到终态的行为链路；
- 已形成含反证和 Claim 上限的初始候选池。

完成后，岗位只执行四类动作：选择、排序、术语翻译、删除弱信号。岗位不能改变实现事实、归属、数字或验证层级。

## 4. 岗位画像

写一句内部定位：

```text
把候选人呈现为【目标岗位】，用【主经历】证明【核心能力】，用【第二经历】补足【能力缺口或差异化】。
```

常见主线：

| 目标岗位 | 第一屏应证明 | 容易误伤的内容 |
| --- | --- | --- |
| Java / 业务后端 | 业务建模、数据库、缓存、事务、MQ、一致性和稳定性 | 只有名词、没有链路的高并发模板项目 |
| Python / AI 应用后端 | 模型如何进入业务流程、接口、数据、工作流、检索与失败兜底 | 大量算法术语或纯 Java 八股项目 |
| Agent 工程 / Harness | Runtime、工具、上下文、状态、恢复、审计和评测 | 聊天壳、Tool Calling Demo、泛 RAG |
| RAG / 知识库 | 数据处理、检索、重排、引用、评测与服务化 | 只写“接入向量库降低幻觉” |
| 算法 / 科研 | 问题、数据、baseline、方法、实验、消融和个人贡献 | 泛工程功能和无关框架 |
| 垂直行业 AI | 行业对象、工作流程和领域约束，再写 AI 技术 | 抹掉领域背景后变成同质化 Agent |

若同时具备多条路线，默认生成一个主版本。只有用户明确要求或岗位差异确实会改变项目组合时才生成第二版。

## 5. 项目评分

项目评分发生在每个仓库都完成轻量发现之后。评分不向用户展示，也不设置未经校准的硬阈值。

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
| --- | --- | --- | --- | --- |
| 岗位匹配 | 无关 | 边缘相关 | 直接相关 | 覆盖核心工作 |
| 责任清晰 | 无法判断 | 参与 | 负责明确模块 | 负责关键链路或设计 |
| 技术故事 | 只有功能 | 有机制 | 有失败与边界 | 有取舍、验证和闭环 |
| 可验证性 | 只有宣传 | 有说明或代码 | 有测试/实验 | 有复现、发布或真实反馈 |
| 差异化 | 通用模板 | 常见题材 | 场景或技术有特色 | 与候选人背景形成稀缺组合 |
| 面试可讲性 | 一问即穿 | 只能讲功能 | 可讲 5–10 分钟 | 可讲 15–20 分钟并回答取舍 |

再扣除风险：

- 与另一个项目证明相同能力；
- 大量无法解释的技术或数字；
- 项目范围明显大于个人职责；
- 与目标岗位相反的面试入口；
- 强候选依赖旧 revision、第三方归属或过期 benchmark。

分数只用于相对比较，不代表模型效果或录用概率。

## 6. 项目组合与排序

默认选择 1–2 个能够形成清晰岗位画像的项目；第三个项目只有在增加明显能力覆盖且版面允许时才保留。

常见组合：

- **真实实习 + 个人项目**：实习证明真实业务和协作，个人项目证明端到端设计；
- **业务后端 + Agent 项目**：后端证明工程基础，Agent 证明 AI 方向能力；
- **垂直领域项目 + 通用工程项目**：前者提供差异化，后者提供岗位可迁移性；
- **科研 + 工程项目**：科研证明问题和实验，工程项目证明服务化与交付。

排序原则：

1. 最能解释目标岗位的项目放前面；
2. 真实且相关的实习通常优先于同质化课程项目；
3. 第一项目承担核心岗位画像，第二项目补缺口，不重复第一项目；
4. 品牌不能替代职责；
5. 候选人答不住的项目不做主项目；
6. 项目内部 bullet 数由新增信号决定，不用“三条下限”影响项目去留。

## 7. JD 定制

建立内部映射：

```text
JD 信号 → 已发现项目 → 已存在事实 → 选材/排序/表达动作 → 面试风险
```

JD 只能：

- 调整项目选择和顺序；
- 将内部术语翻译成岗位熟悉的语言；
- 强调已有能力中与 JD 相符的部分；
- 删除会干扰岗位主线的内容；
- 选择真实使用且能回答的技术栈。

JD 不能：

- 添加材料中没有的技术；
- 把了解写成熟练、参与写成主导；
- 把本地实验写成生产经验；
- 把团队结果全部归给个人；
- 回头改变 Repository Map 或行为链路的事实集合。

## 8. 完成标准

- 岗位排序发生在仓库事实发现与候选竞争之后；
- 能用一句话说明候选人的岗位画像；
- 第一项目直接证明核心岗位能力；
- 后续项目与第一项目分工明确；
- 删除项目有可解释理由：弱相关、重复、追问风险或责任不清；
- JD 只改变选材、排序和语言，没有改变事实集合；
- 没有用 bullet 数量下限替代故事质量判断。
