## 1. Project Fact Card

写作前在内部整理以下字段。未知可以保留为空，不要补造。

| 字段 | 要回答的问题 |
| --- | --- |
| 项目身份 | 项目名、类型、时间、当前版本或材料范围是什么 |
| 目标岗位 | 这段经历要证明哪类岗位能力 |
| Actor | 谁使用或依赖这个系统 |
| Trigger | 什么事件触发这条链路 |
| Input | 系统接收什么请求、数据或任务 |
| Core Flow | 正常情况下经过哪些关键步骤 |
| Output | 产出什么可观察结果 |
| Failure | naive 实现会在哪里失败 |
| Constraint | 并发、时延、数据量、一致性、安全或成本约束是什么 |
| Ownership | 候选人负责哪一段、与谁协作 |
| Design | 为失败模式补了什么机制 |
| Trade-off | 为什么选它、不选什么、付出什么代价 |
| Validation | 如何测试、压测、评测、验收或复盘 |
| Result | 有什么有边界的结果 |
| Unknown | 哪些信息缺失且可能改变措辞 |

## 2. 业务场景模型

使用以下链条理解项目：

```text
Actor → Trigger → Input → Core Flow → Failure → Constraint → Output → Value
```

### Actor

优先写具体角色：用户、商家、运营、内部研发、值班工程师、算法研究员、硬件工程师、下游系统。不要只写“企业”“平台用户”。

### Trigger 与 Input

说明什么时候发生、输入是什么，例如：

- 用户参与拼团并提交支付；
- 开发者提交代码修改任务；
- 值班人员收到告警并开始排障；
- 研究员提出跨章节技术手册问题；
- 模型版本更新后触发回归评测。

### Core Flow

只保留 4–7 个决定系统行为的步骤。页面、Controller、Service、DAO 不是业务链路；资格校验、库存预占、订单创建、支付确认、成团结算才是。

### Failure 与 Constraint

把“技术亮点”还原成它要避免的失败：

| 技术名词 | 更有价值的失败模式 |
| --- | --- |
| Redis Lua | 库存与资格校验分离导致竞态或超卖 |
| MQ | 同步主链路阻塞、下游短暂失败、事件需要重试 |
| Rerank | 向量召回候选相关性不足 |
| Checkpoint | 长任务中断后无法从可靠状态恢复 |
| Tool Registry | 模型参数不可控、工具返回难统一 |
| 状态机 | 正逆向流程停留在无法收敛的中间状态 |

### Output 与 Value

结果优先写可观察行为：订单进入一致终态、用户获得可引用回答、任务可以恢复、排障过程可复盘。只有真实材料支持时才上升到营收、转化、人效或生产影响。

## 3. 没有真实业务时的安全写法

个人项目、开源项目和基础设施项目不一定有真实用户。此时使用任务场景：

```text
面向【任务角色】在【执行环境】中的【反复失败】，设计【系统行为】，重点控制【约束】，并以【验证方式】确认边界。
```

例如：

> 面向代码仓库中的长链路修改任务，设计本地 Coding Agent Runtime，统一上下文构造、受控工具执行、状态恢复与运行记录，重点处理多轮任务中的上下文膨胀、工具副作用和中断后状态丢失。

不要把个人项目写成“服务企业客户”“支撑生产流量”“显著提升团队效率”，除非材料明确支持。

## 4. 项目标题与描述

### 标题

使用：

```text
业务或任务领域 + 核心系统对象｜个人角色
```

优先：

- 拼团营销交易系统｜Java 后端开发
- 面向运维排障的故障诊断 Agent｜AI 应用开发
- 面向代码仓库任务的本地 Agent Harness｜Agent 工程
- 面向 IC 技术手册的 GraphRAG 问答系统｜AI for IC

避免：

- 企业级高并发分布式平台；
- 通用型智能体服务平台；
- Spring Boot + Redis 项目；
- 冒用真实公司或产品名称的学生项目；
- “vibe coding”“数字分身”等降低工程边界的词。

### 项目描述

项目描述承担四件事：场景、核心链路、系统边界、个人职责。推荐 1–2 句，不把所有机制和指标塞进去。

```text
面向【角色】在【流程】中的【问题】，负责【系统或链路】，覆盖【关键步骤】，重点处理【失败模式或约束】。
```

## 5. 候选故事

从 Fact Card 中最多选 3–6 个候选故事：

| 故事类型 | 证明什么 | 常见内容 |
| --- | --- | --- |
| 核心链路 | 懂业务或任务生命周期 | 状态、实体、流程、输入输出 |
| 关键难点 | 能定位并解决具体问题 | 超卖、慢查询、召回差、状态丢失 |
| 异常边界 | 不只实现 happy path | 重复、超时、漂移、越权、降级 |
| 方案取舍 | 有工程判断 | 强一致与最终一致、规则与模型 |
| 验证结果 | 不是凭感觉优化 | 测试、压测、benchmark、验收 |
| 排障闭环 | 能处理真实故障 | 监控、日志、复现、修复、回归 |

一个故事只围绕一个失败模式。多个机制共同处理同一个失败时可以合并；同一机制解决不同失败时按主价值选择一个。

为每个候选故事在内部写一个语义签名：

```text
业务对象 × 失败/约束 × 关键决策 × 可观察结果
```

先过四个硬门槛：来自现有材料、能指出本人或项目动作、能说明改变了什么系统行为、能够解释基本流转或验证。未通过时先缩小措辞、合并或删除，不靠华丽词汇补齐。

通过后按岗位相关性、核心链路位置、技术判断、失败处理、验证强度、差异化和面试可讲性排序。简单登录、普通 CRUD 和框架搭建不能挤掉状态、一致性、恢复、评测或真实排障故事。最终目标是 3–5 条：多项目中的次要项目不足三个独立故事时优先删除；唯一项目或用户明确要求保留时可以少写并追问关键缺口，不把一个故事机械拆成三条。

## 6. Bullet 结构、排序与去重

### 常用结构

根据事实选择句式，不要所有 bullet 套同一个模板：

```text
负责【核心链路】，覆盖【关键步骤】，使【业务或任务状态】可以完整流转。
针对【具体失败】，通过【关键机制】控制【约束或后果】。
采用【方案】而非【替代方案】，以【边界措施】平衡【收益与代价】。
在【明确条件】下，以【测试/评测】验证【可观察行为或结果】。
结合【监控/日志/trace】定位【故障根因】，完成【修复与回归】。
```

### 默认排序

1. 核心链路或领域建模；
2. 最强技术难点；
3. 异常、一致性、安全或可靠性；
4. 验证、指标或排障闭环；
5. 另一条不重复且岗位相关的强故事。

### 去重规则

- 项目描述说过的整体定位，不在第一条原样重复。
- 两条 bullet 不围绕同一个失败模式。
- 同一技术名词不要反复出现；写它造成的系统行为。
- 每条最多保留一个主要结论，避免同时讲架构、性能、安全和评测。
- 两条高度相似时，保留责任更清楚、验证更强或岗位更相关的一条。
- 第一条不要默认写“搭建项目整体架构”；只有架构边界本身是核心贡献时才写。
- 删除任意一条后，如果没有损失独立业务问题、工程能力或面试故事，这条就不应单独保留。
- 验证通常并入对应的设计 bullet；只有跨多条链路的独立压测、评测或质量体系，才单独占一条。

### 语言强度

- 使用“负责、设计、实现、重构、优化、定位、推动、验证”等明确动作。
- 避免“参与了、完成了、使用了”连续出现，但不要为了强动词冒领主导权。
- 避免“全面、极致、企业级、工业级、海量、高可用、显著、大幅”等无边界营销词。
- 先写可观察行为，再写内部模块名；一条内最多保留 1 个项目内部术语和 2–3 个通用技术术语。

## 7. 技术栈

只保留满足以下至少一项的技术：

- 直接参与核心链路；
- 对目标岗位是重要筛选信号；
- 在 bullet 中有对应设计或实现；
- 候选人能够回答原理、使用方式和失败边界。

删除：

- 只在依赖文件中出现、本人未使用的技术；
- 与目标岗位无关的工具清单；
- 会主动引出候选人答不住的深水区；
- 同义框架和 AI 编程工具的堆叠。

## 8. 完成标准

- 项目标题能够让非项目成员理解对象和边界。
- 项目描述包含场景、链路、边界和职责，但不堆机制。
- 目标 3–5 条 bullet，各自证明不同能力；事实不足时不凑数。
- 每条可以还原为场景、失败、动作、边界和验证。
- 没有真实业务时使用任务场景，没有虚构用户和影响。
- 技术栈中的每个词都能在正文或面试中解释。
