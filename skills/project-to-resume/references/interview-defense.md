# 面试防御与项目展开

## 1. 防御卡目的

简历 bullet 是索引，不是完整答案。用户要求面试准备时，为每条 bullet 生成一张防御卡，并与原 bullet 和事实来源保持一致。

## 2. Defense Card Schema

```text
Bullet：
证明的岗位能力：
业务/任务场景：
本人职责边界：
输入与输出：
核心流程或状态流：
主要失败模式：
关键设计：
数据结构 / schema / 状态字段：
异常与失败路径：
替代方案：
取舍：
验证方式：
指标口径：
证据或可演示材料：
不能越界的说法：
高频追问：
```

不要求每个字段都很长，但未知项必须暴露。不能回答关键字段时，回到简历正文删除或降级该 bullet。

## 3. 三层项目讲法

### 30 秒

回答：服务谁、解决什么问题、系统怎么工作、本人最核心的贡献是什么。

```text
这是一个面向【角色/任务】的【系统】。原来的主要问题是【失败模式】。我负责【链路】，重点通过【关键设计】处理【约束】，并用【验证】确认结果。
```

### 3 分钟

按以下顺序：

1. 场景和目标；
2. 核心链路；
3. 两个最关键的难点；
4. 一次取舍；
5. 验证和结果；
6. 边界和下一步。

### 15–20 分钟

准备沿任意一条 bullet 展开：

```text
为什么有这个问题 → naive 方案怎么失败 → 你的方案 → 数据/状态怎么流 → 异常怎么办 → 为什么不用另一方案 → 怎么验证 → 还有什么边界
```

## 4. 追问树

为每条 bullet 至少生成：

- 一个“为什么”问题；
- 一个“具体怎么做”问题；
- 一个异常/失败问题；
- 一个替代方案问题；
- 一个数字或验证问题；
- 一个个人职责问题。

不要只生成概念八股。追问必须绑定当前项目对象。

## 5. 应准备的辅助材料

按项目类型选择：

- 系统架构图；
- 核心时序图；
- 状态机或数据流图；
- 表结构、Redis Key、消息体或工具 schema；
- 一次 trace / 日志 / 运行工件；
- 压测、benchmark 或评测报告；
- badcase 分类；
- 一个失败实验或未采用方案；
- 一段可公开演示或部署说明。

这些材料用于面试准备，不默认塞进简历。

## 6. 数字防御

每个数字必须能回答：

- 测什么；
- 为什么选这个指标；
- baseline 是什么；
- 样本和负载是什么；
- 环境和版本是什么；
- 如何计算；
- 谁或什么 verifier 判断成功；
- 局部指标提升时主任务是否保持；
- 原始结果在哪里。

答不上时，将数字从简历正文移除，但可以保留为后续测量计划。

## 7. 故障故事

真实故障使用：

```text
现象 → 影响 → 初始假设 → 监控/日志 → 复现 → 根因 → 修复 → 回归 → 防复发
```

区分真实发生、测试复现、设计风险和假设。不要把设计考虑包装成线上事故。

## 8. 反向降级规则

出现以下任一情况，回写简历并降级：

- 无法说清输入输出和核心状态；
- 技术与失败模式没有因果关系；
- 说不出本人负责边界；
- 只有框架名，没有具体实现或配置；
- 指标没有 baseline、样本或定义；
- 无法解释一个合理替代方案；
- 表述依赖不可披露信息才能成立；
- 项目范围明显大于候选人可解释内容。

面试防御不是为夸张表述补话术，而是反向检查简历是否诚实、具体、可讲。
