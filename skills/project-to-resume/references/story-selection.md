# Story Hypothesis、候选竞争与淘汰

本文件接收 Repository Map、行为链路、测试发现和必要的历史差异，负责把“仓库事实”收敛为少量值得进入简历的工程故事。它不负责全量仓库总结。

## 1. 为什么需要 Story Hypothesis

代码中存在一个组件，只说明它可能有用。简历故事还必须回答：

```text
谁遇到什么任务或失败
→ 系统需要产生什么行为
→ 项目做了什么关键判断或变化
→ 结果在哪个边界内可观察
→ 当前证据允许说到什么程度
```

因此，先写可被证伪的 Story Hypothesis，再决定是否生成 bullet。

示例：

- 弱：项目使用 Redis Stream。
- 假设：同步下单后仍存在异步任务；项目用可重放消费状态、幂等边界和补偿处理重复或短暂失败，使订单能够进入明确终态。

第二种可以被源码、测试和反证检查；第一种只是技术名词。

## 2. Story Card

每个候选使用轻量内部卡片：

```text
Story ID
外部问题或任务
行为链路
关键失败或约束
设计或变化
源码与测试锚点
当前实现、历史变化或 upstream delta
验证状态
个人归属来源
允许的 Claim 上限
对应岗位能力
反证
未知项
```

字段含义：

- **外部问题或任务**：非项目成员也能理解的目标；
- **行为链路**：入口到终态，不是文件列表；
- **失败或约束**：naive 方案会在哪里失效；
- **设计或变化**：项目作出的关键决策，不是框架默认行为；
- **锚点**：源码、测试、运行、commit 或 upstream 的固定位置；
- **验证状态**：设计、实现、测试源码、测试运行、有界测量、发布/使用分层；
- **个人归属**：用户陈述、本地项目假设、可见贡献、项目级或未知；
- **Claim 上限**：最终允许使用的最强动词和结果；
- **反证**：与故事冲突的路径、版本、测试或文档；
- **未知项**：会改变故事或措辞但尚未解决的信息。

Story Card 默认不向用户展示。

## 3. 先找反证，再做竞争

为每个假设主动检查：

- 该机制是否只存在于未调用代码、实验目录或示例中；
- README 是否描述了尚未实现的路线图；
- 测试 fixture 是否与当前生产代码分支不同；
- benchmark 是否绑定旧 commit、不同模型或不同负载；
- 当前实现是否绕过了声称的状态或权限边界；
- upstream 是否已具备同一能力；
- 个人归属是否只来自仓库所有者或提交者推断；
- 是否有更简单解释，例如框架自动提供而非项目设计。

发现反证不一定淘汰故事，但必须降低 Claim、缩小范围或提出针对性问题。

## 4. 候选竞争维度

不要设置未经校准的总分阈值。按以下维度做相对比较：

| 维度 | 强候选表现 | 弱候选表现 |
| --- | --- | --- |
| 核心性 | 位于主要任务链路，影响状态或终态 | 边缘页面、普通配置、便利功能 |
| 工程判断 | 有失败、约束、取舍或所有权设计 | 框架默认能力、机械接入 |
| 行为变化 | 能说明系统行为如何不同 | 只说明“使用了某技术” |
| 证据可追踪 | 有固定源码/测试/历史锚点 | 只有宣传或模糊描述 |
| 反证韧性 | 检查版本与替代解释后仍成立 | 依赖旧实验或矛盾材料 |
| 个人归属 | 有用户陈述或可见贡献边界 | 只知道项目存在 |
| 独立信号 | 与其他候选证明不同能力 | 同一失败被拆成多条 |
| 面试可讲 | 可讲场景、链路、取舍和验证 | 只能解释 API 用法 |
| 岗位价值 | 在后置排序中提供核心信号 | 只命中关键词 |

比较顺序：先核心性、工程判断、证据和反证，再看岗位价值。JD 不能救活一个事实薄弱的候选。

## 5. 区分框架默认能力与项目设计

遇到高级组件时问：

1. 项目是否改变了它的默认使用方式？
2. 它控制了哪个具体失败或约束？
3. 是否存在项目自己的状态、策略、补偿、权限或验证？
4. 删除该设计后，系统会以什么可观察方式失败？

若答案只是“框架支持，所以项目也支持”，通常不作为主故事。

可成为故事的例子：

- 不只是“用了 MQ”，而是定义业务提交、消息记录、幂等消费与补偿边界；
- 不只是“用了向量库”，而是处理更新/删除传播、权限过滤、低相关拒答和固定评测；
- 不只是“有 Agent Loop”，而是显式区分终态、受控工具副作用、上下文预算和恢复；
- 不只是“有重试”，而是按失败类型、状态与副作用决定是否重试，并限制预算。

## 6. 语义去重

为每个候选写语义签名：

```text
业务/任务对象 × 失败或约束 × 关键决策 × 可观察结果
```

出现以下情况时合并：

- 两条围绕同一个失败，只是分别写 Redis、Lua、锁；
- 项目描述已经完整承担该定位；
- 验证只是某设计的直接证据，没有形成独立质量体系；
- 同一状态机被拆成正向、异常、补偿三个近义 bullet；
- 多个入口共享同一 Runtime，只是重复列 CLI、TUI、Gateway。

保留责任更清楚、失败更具体、证据更强、面试空间更大的版本。

## 7. 淘汰原因

内部为未选候选记录一个主要原因：

- `peripheral`：外围功能，未进入核心任务链路；
- `framework-default`：主要是框架默认能力；
- `weak-evidence`：只有 README、proposal 或模糊说明；
- `counterevidence`：当前 revision 存在明显反证；
- `stale-measurement`：数字属于旧 commit、不同环境或不同 workload；
- `ownership-unknown`：无法连接到候选人个人动作；
- `duplicate`：与更强故事语义重复；
- `role-weak`：事实成立，但对目标岗位没有新增信号；
- `interview-risk`：候选人难以解释关键机制、替代方案或边界；
- `stronger-alternative`：有限版面中存在更强候选。

淘汰记录用于内部复核，不默认展示给用户。

## 8. 岗位与 JD 后置排序

候选池形成并通过反证后，再应用岗位：

- 选择能直接证明岗位核心工作的故事；
- 将内部术语翻译成招聘者熟悉的系统行为；
- 让多个项目承担互补能力；
- 删除只重复关键词、不增加能力覆盖的候选；
- 使用领域 Playbook 检查异常路径、验证与取舍是否遗漏。

JD 可以改变：选择、顺序、技术栈取舍、语言角度。

JD 不可以改变：实现事实、个人归属、数字口径、测试状态、上线状态、业务结果。

## 9. Claim 上限

每张 Story Card 在进入成稿前必须声明上限：

| 当前来源 | 允许上限示例 |
| --- | --- |
| README / 设计文档 | “面向…设计目标”，不能写已实现 |
| 当前源码 | “实现/区分/限制/支持某确定性行为” |
| 测试源码 | “编写/包含某类测试场景” |
| 可归属运行记录 | “在固定 revision 和环境下指定场景通过” |
| benchmark | “在固定样本/负载下从 A 到 B” |
| 发布或真实使用来源 | 在来源边界内写发布、使用或观察结果 |

个人动词还需要归属来源。项目级能力与个人贡献分别判断。

## 10. 最终选择与 Bullet 停止条件

按强到弱逐条加入候选。每加入一条，问：

> 它是否增加了新的岗位信号、核心行为、失败边界、工程判断、验证闭环或独立面试故事？

答案是否定时停止。

规则：

- 每个项目可保留 1–5 条，没有三条下限；
- 只有两个强故事就写两条；只有一个可归属强故事就写一条；
- 不拆分同一机制、不重复同一价值、不抬高外围功能、不制造数字；
- 多项目分别判断，次要项目只有在整体岗位画像中增加独立信号才保留；
- 最终条数不是质量目标，故事密度和可追问性才是。

## 11. 选择完成标准

- 每个入选故事位于可解释的行为链路；
- 每个故事有失败或约束，而不只是组件名；
- 已主动检查反证、版本错位和 upstream；
- 个人归属和 Claim 上限明确；
- 入选故事之间语义独立；
- 淘汰故事有可解释原因；
- 岗位与 JD 只在候选形成后介入；
- 下一条候选无法增加新的岗位信号时已经停止。
