# Story Selection

本文件把 Repository Map、行为链路、测试发现和必要历史收敛为少量值得写进简历的工程故事。

## 1. Story Hypothesis

组件存在不等于故事成立。候选必须能写成：

```text
谁遇到什么任务或失败
→ 系统需要产生什么行为
→ 项目做了什么关键判断或变化
→ 结果在哪个边界内可观察
→ 当前证据允许说到什么程度
```

弱候选：

> 使用 Redis Stream。

可验证的假设：

> 业务提交后仍有异步任务；项目通过可重放消费状态、幂等边界和补偿处理重复或短暂失败，使核心对象能够收敛到明确终态。

## 2. Story Card

每个候选在内部记录：

```text
Story ID
外部问题或任务
行为链路
关键失败或约束
设计或变化
源码与测试锚点
当前实现 / 历史变化 / upstream delta
验证状态
个人归属来源
允许的 Claim 上限
岗位能力
反证
Unknown
```

Story Card 是推理工具，不进入默认输出，也不能为了填满字段制造事实。

## 3. 先找反证

主动检查：

- 机制是否只在未调用代码、示例、实验目录或 feature flag 后；
- README 是否描述路线图而非当前能力；
- 测试是否针对不同 revision、mock 路径或已废弃接口；
- benchmark 是否绑定旧 commit、不同模型、负载或样本；
- 主路径是否绕过声称的状态、权限或恢复边界；
- upstream 或框架是否已提供同一能力；
- 个人归属是否只由仓库 owner、commit author 或目录推断；
- 是否存在更简单解释，例如默认配置而非项目设计。

反证不一定淘汰候选，但必须导致缩小范围、降低 Claim 或提出具体问题。

## 4. 相对竞争

不使用未经校准的总分或通过率。候选按相对强弱比较：

| 维度 | 强候选 | 弱候选 |
| --- | --- | --- |
| 核心性 | 位于主任务链路并影响状态或终态 | 边缘页面、脚手架、普通配置 |
| 工程判断 | 有失败、约束、取舍或所有权设计 | 框架默认、机械接入 |
| 行为变化 | 能说明系统如何不同 | 只说明使用某技术 |
| 证据 | 有固定源码、测试、运行或历史锚点 | 只有宣传或模糊描述 |
| 反证韧性 | 版本与替代解释检查后仍成立 | 依赖旧实验或矛盾材料 |
| 个人归属 | 用户陈述或贡献边界明确 | 只知道项目存在 |
| 独立信号 | 与其他候选证明不同能力 | 同一失败拆成多条 |
| 面试深度 | 可讲链路、取舍、代价和验证 | 只能解释 API 用法 |
| 岗位价值 | 后置排序时证明核心工作 | 只命中关键词 |

先比较核心性、工程判断、证据和反证，再应用岗位价值。JD 不能救活事实薄弱的候选。

## 5. 框架默认能力

遇到高级组件时问：

1. 项目是否改变默认使用方式；
2. 它控制哪个具体失败或约束；
3. 是否存在项目自己的状态、策略、补偿、权限或验证；
4. 删除该设计后会出现什么可观察失败。

若答案只是“框架支持，所以项目也支持”，通常不占主 bullet。

## 6. 语义去重

为每个候选写语义签名：

```text
业务/任务对象 × 失败或约束 × 关键决策 × 可观察结果
```

以下情况合并或淘汰：

- 同一失败分别写锁、Lua 和 Redis；
- 项目描述已经完整承担该定位；
- 验证只是设计的直接证据，没有形成独立质量体系；
- 同一状态机被拆成正向、异常和补偿三个近义 bullet；
- 多个入口共享同一 Runtime，却重复列 CLI、TUI、Gateway；
- 两条句子换了技术名词，但对招聘者证明同一能力。

保留责任更清楚、失败更具体、证据更强、面试空间更大的版本。

## 7. 个人归属门

系统故事与个人故事分别判断：

```text
项目是否具备该能力？
候选人是否负责该能力？
```

只有第一项成立时：

- 可作为项目理解和追问材料；
- 默认使用项目主语；
- 不进入个人强动词 bullet，除非用户确认职责。

fork、模板和团队项目还要回答：

```text
upstream / 团队已有能力
→ 候选人新增、修改、集成或验证
```

## 8. Claim ceiling

| 来源 | 允许上限 |
| --- | --- |
| README / 设计文档 | 定位、目标、设计意图 |
| 当前源码 | 实现、区分、限制、持久化等确定性行为 |
| 测试源码 | 编写或包含某类测试场景 |
| 可归属运行记录 | 指定 revision 和环境下的实际结果 |
| benchmark | 固定样本、负载和 baseline 下的有界测量 |
| 发布或真实使用来源 | 在来源范围内描述发布或使用 |

个人动词还需要归属来源。不得用低层证据支持高层效果。

## 9. 淘汰原因

- `peripheral`：外围能力；
- `framework-default`：框架默认；
- `weak-evidence`：只有说明或宣传；
- `counterevidence`：反证成立；
- `stale-measurement`：数字与当前 revision 不匹配；
- `ownership-unknown`：无法连接个人职责；
- `duplicate`：语义重复；
- `role-weak`：事实成立但不增加岗位信号；
- `interview-risk`：无法解释取舍或边界；
- `stronger-alternative`：存在更强候选。

淘汰清单用于内部复核，不默认展示。

## 10. 岗位后置排序

候选池稳定后，目标岗位和 JD 可以：选择和排序故事、翻译术语、选择技术栈、删除弱相关内容、让多个项目承担互补能力。

不可以改变：实现事实、个人归属、数字口径、测试运行状态、发布或业务结果。

## 11. 停止条件

按强到弱加入候选，每加入一条问：

> 它是否增加新的岗位信号、核心行为、失败边界、工程判断、验证闭环或独立面试故事？

若否，停止。

- 每个项目 1–5 条；
- 两个强故事就写两条；
- 一个可归属强故事就写一条；
- 不拆分同一机制、不重复价值、不抬高外围功能、不制造数字；
- 项目描述与 bullet 也要去重；
- 最终条数不是质量目标，故事密度和可追问性才是。

## 完成标准

- 每个入选故事位于可解释的行为链路；
- 每个故事有失败或约束，不只是组件名；
- 已检查反证、版本和 upstream；
- 个人归属与 Claim ceiling 明确；
- 入选故事之间语义独立；
- 淘汰故事有可解释原因；
- 岗位与 JD 只在候选形成后介入；
- 下一条不再增加独立信号时已经停止。
