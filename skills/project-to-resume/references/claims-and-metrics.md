## 1. 默认轻量 Claim Record

普通简历生成也要在内部记录最小事实边界，但不要默认展示：

| 字段 | 内容 |
| --- | --- |
| Claim | 想写进简历的外部可理解结论 |
| 来源 | 用户说明、现有简历、源码、测试结果、报告等 |
| 归属 | 用户陈述、贡献可见、项目级、未知、冲突 |
| 强度 | 意图、实现、验证、测量、上线/真实使用 |
| 数字口径 | 指标、baseline、负载、样本、环境、公式、来源 |
| 边界 | 证明什么、没有证明什么 |
| 处理 | 可写、缩小、追问后升级、拒绝 |

用户没有要求核验时，不要求外部证据齐全；仍要保证最终措辞不强于当前来源。

## 2. 事实强度与允许措辞

| 强度 | 常见来源 | 可以写 | 不可以自动写 |
| --- | --- | --- | --- |
| 意图 / 设计 | README、方案、issue | 面向、计划、设计目标 | 已实现、已验证、产生效果 |
| 实现存在 | 源码、配置、契约 | 实现、支持、构建、封装；描述确定性分支行为 | 提升、保障、生产可用 |
| 行为验证 | 测试通过、运行记录 | 验证、在固定场景通过 | 普遍可靠、线上有效 |
| 有界测量 | benchmark、压测、实验 | 在指定负载/样本下从 A 到 B | 生产效果、因果推广 |
| 发布 / 真实使用 | 发布产物、线上观测、用户陈述 | 上线、支撑、在观察窗口内 | 更广范围或长期稳定性 |

动词强度从低到高：

```text
参与/协助 → 负责/实现 → 设计/重构 → 主导/推动 → 上线/支撑 → 提升/降低
```

不要为了简历好看自动升级动词。

“设计”同时包含技术判断和个人归属。源码可以证明结构存在；只有用户明确职责、设计记录或可见贡献同时成立时，才把个人动词升级为“设计”。测试文件本身只支持“编写/补充某类测试用例”，不支持“测试覆盖、验证通过”。

## 3. 个人归属

| 情况 | 默认处理 |
| --- | --- |
| 用户明确说“我的项目”“我负责” | 视为用户陈述，使用与其描述一致的个人动词 |
| 现有简历明确写个人职责 | 可作为普通草稿来源；核验模式再检查外部支持 |
| 在简历语境中提供本地仓库或当前工作区 | 暂按候选人项目处理；只对源码可见实现使用普通个人动词 |
| 只提供公开 URL、明显第三方或团队仓库 | 先用项目主语并区分上游/团队能力；必要时追问一次职责 |
| 用户说明是开源贡献 | 区分上游能力与本人新增 PR、模块或集成 |
| 团队/实习项目 | 先写本人负责链路，再写团队结果；不把团队规模全部归个人 |
| 材料冲突 | 使用更窄措辞并询问，不自行选择更强版本 |

“提交者”不自动等于设计者或负责人；“仓库作者”也不自动等于候选人。

## 4. 数字资格

一个效果数字至少要能回答：

| 字段 | 问题 |
| --- | --- |
| 指标对象 | 到底测的是什么：P95、Recall@5、通过率、人工耗时等 |
| 定义 | 分子、分母、统计窗口和单位是什么 |
| Baseline | 与哪个方案、版本或流程比较 |
| Workload | 数据量、并发、任务类型、请求分布是什么 |
| Sample | Case 数、查询数、运行次数或用户数是多少 |
| Environment | 机器、模型、配置或版本是否固定 |
| Formula | 百分比和聚合方式如何计算 |
| Source | 压测、监控、日志、评测脚本、报告还是用户陈述 |
| Success Gate | 局部指标变好时，正确性或任务成功是否保持 |

普通草稿不要求把整张表写进简历，但必须能够理解数字含义。缺失会改变含义时先输出无数字版本，再问一个问题。

## 5. 特殊数字处理

### 百分比

- “提升 X%”必须知道 baseline 和最终对象。
- 区分百分点和相对提升：`40% → 50%` 是提升 10 个百分点或相对提升 25%。
- 区分“两个均值之比”和“逐样本比例平均”；两者冲突时不自行选择，删除比例并追问计算方式。

### 100% 与零

- 小样本固定用例优先写 `10/10 个恢复场景通过`，不要泛化为“识别率 100%”。
- “零故障、零重复、零泄漏”必须带统计对象和观察窗口。
- 多个 100% 指标同时出现时，优先保留最能证明核心失败模式的一项。

### 工程覆盖计数

“2 类模型、7 类工具、3 类运行产物”属于工程规模，不是效果指标。满足以下条件时可以写：

- 每一类能逐项解释；
- 数量体现架构扩展或覆盖范围；
- 没有挤掉更强的业务、故障和验证故事。

### 小样本 AI 评测

- 样本很小时，可以写“在 12 条固定 QA 上完成评测”，不要包装成普遍模型质量。
- RAGAS、LLM-as-Judge 等指标要说明评估模型、版本和配置，至少在面试材料中可回答。
- 只报最高值、最好样本或单次运行时，默认不作为主效果结论。

### 配置数字

超时、重试次数、缓存 TTL、并发阈值和预算上限是设计参数，不是性能结果。写它们时必须解释为什么设置和如何验证。

## 6. 无数字写法

没有可信数字时，优先写：

- 业务或任务链路覆盖；
- 失败模式与处理机制；
- 正常与异常状态能够收敛；
- 将非关键工作移出主链路；
- 统一参数、状态和错误返回；
- 支持自助查询、回放、审计或问题定位；
- 构建固定测试、压测或评测方法；
- 沉淀可复用的模板、规则或工具。

避免使用“显著提升、大幅降低、有效保障、极致优化”等没有数字也没有边界的效果词。

## 7. 默认写作与严格核验的分界

### 默认写作

- 接受用户简历和补充说明为用户陈述。
- 对含义清楚的数字可以保留，并把口径问题留到面试准备。
- 对含义冲突或明显无法解释的数字先降级。
- 内部记录 Claim Record，不展示证据表。

### 严格核验

用户明确说“核验、验真、审计、确认数字是否真实”时，读取 [evidence-rules.md](evidence-rules.md)：

- 固定 revision；
- 检查 evidence class；
- 区分源码、测试、运行、benchmark、发布和线上；
- 输出逐条裁决和证据映射。

不要把严格核验变成普通求职者获得第一版简历的前置门槛。

## 8. 完成标准

- 每个数字能解释指标对象和比较含义。
- 每个个人动词都有用户陈述或贡献来源。
- 实现、验证、测量、上线和生产没有混为一层。
- 100%、零和百分比没有脱离样本、baseline 或统计窗口。
- 没有数字时仍能写出具体机制和边界，而不是空泛效果词。
