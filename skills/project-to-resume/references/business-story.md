# 业务场景、项目故事与 Bullet 设计

本文件负责把已经完成竞争的 Story Card 翻译成招聘者能理解的场景、项目描述和 bullet。陌生仓库探索见 [repository-discovery.md](repository-discovery.md)，候选竞争见 [story-selection.md](story-selection.md)。

## 1. Project Fact Card

写作前在内部整理以下字段。Repository-first 任务中的事实应来自 Repository Map 和行为链路；目标岗位只参与后置排序。未知可以保留为空，不要补造。

| 字段 | 要回答的问题 |
| --- | --- |
| 项目身份 | 项目名、类型、时间、当前版本或材料范围是什么 |
| Actor | 谁使用或依赖这个系统 |
| Trigger | 什么事件触发这条链路 |
| Input | 系统接收什么请求、数据或任务 |
| Core Flow | 正常情况下经过哪些关键步骤 |
| Output | 产出什么可观察结果 |
| Failure | naive 实现会在哪里失败 |
| Constraint | 并发、时延、数据量、一致性、安全或成本约束是什么 |
| Ownership | 候选人负责哪一段、与谁协作 |
| Design | 为失败模式补了什么机制 |
| Trade-off | 为什么选它、不选什么、付出什么代价 |
| Validation | 如何测试、压测、评测、验收或复盘 |
| Result | 有什么有边界的结果 |
| Unknown | 哪些信息缺失且可能改变措辞 |

## 2. 业务场景模型

使用以下链条理解并表达项目：

```text
Actor → Trigger → Input → Core Flow → Failure → Constraint → Output → Value
```

### Actor

优先写具体角色：用户、商家、运营、内部研发、值班工程师、算法研究员、硬件工程师、下游系统。不要只写“企业”“平台用户”。

### Trigger 与 Input

说明什么时候发生、输入是什么，例如：用户参与拼团并提交支付、开发者提交代码修改任务、值班人员收到告警、模型版本更新后触发回归评测。

### Core Flow

只保留决定系统行为的步骤。页面、Controller、Service、DAO 不是业务链路；资格校验、库存预占、订单创建、支付确认、成团结算才是。

### Failure 与 Constraint

把技术名词还原成它要避免的失败：

| 技术名词 | 更有价值的失败模式 |
| --- | --- |
| Redis Lua | 库存与资格校验分离导致竞态或超卖 |
| MQ | 同步主链路阻塞、下游短暂失败、事件需要重试 |
| Rerank | 初步召回候选相关性不足 |
| Checkpoint | 长任务中断后无法从可靠状态恢复 |
| Tool Registry | 模型参数不可控、工具返回难统一 |
| 状态机 | 正逆向流程停留在无法收敛的中间状态 |

### Output 与 Value

结果优先写可观察行为：订单进入一致终态、用户获得可引用回答、任务可以恢复、排障过程可复盘。只有真实材料支持时才上升到营收、转化、人效或生产影响。

## 3. 没有真实业务时的安全写法

个人项目、开源项目和基础设施项目不一定有真实用户。此时使用任务场景：

```text
面向【任务角色】在【执行环境】中的【反复失败】，设计【系统行为】，重点控制【约束】，并以【验证方式】确认边界。
```

不要把个人项目写成“服务企业客户”“支撑生产流量”“显著提升团队效率”，除非材料明确支持。

## 4. 项目标题与描述

### 标题

使用：

```text
业务或任务领域 + 核心系统对象｜个人角色
```

优先：

- 拼团营销交易系统｜Java 后端开发
- 面向运维排障的故障诊断 Agent｜AI 应用开发
- 面向代码仓库任务的本地 Agent Harness｜Agent 工程
- 面向 IC 技术手册的 GraphRAG 问答系统｜AI for IC

避免：企业级高并发分布式平台、通用型智能体服务平台、Spring Boot + Redis 项目、冒用真实公司产品名称的学生项目，以及降低工程边界的宣传词。

### 项目描述

项目描述承担四件事：场景、核心链路、系统边界、个人职责。推荐 1–2 句：

```text
面向【角色】在【流程】中的【问题】，负责【系统或链路】，覆盖【关键步骤】，重点处理【失败模式或约束】。
```

## 5. 从入选故事生成 Bullet

候选形成、反证和淘汰应先在 [story-selection.md](story-selection.md) 完成。这里不再从技术名词现场制造新故事。

每个入选故事只围绕一个外部可理解的问题：

- 核心链路或领域建模；
- 关键故障、性能或效果问题；
- 异常路径、一致性、可靠性或安全边界；
- 方案取舍；
- 验证、评测或业务结果；
- 真实排障闭环。

常用句式：

```text
负责【核心链路】，覆盖【关键步骤】，使【业务或任务状态】可以完整流转。
针对【具体失败】，通过【关键机制】控制【约束或后果】。
采用【方案】而非【替代方案】，以【边界措施】平衡【收益与代价】。
在【明确条件】下，以【测试/评测】检查【可观察行为或结果】。
结合【监控/日志/trace】定位【故障根因】，完成【修复与回归】。
```

## 6. 排序、去重与停止

默认排序：核心链路或最强差异化故事 → 关键失败与工程判断 → 异常/安全/可靠性 → 独立验证或排障闭环。

去重规则：

- 项目描述说过的整体定位，不在第一条原样重复；
- 两条 bullet 不围绕同一个失败模式；
- 同一技术名词不要反复出现，写它改变的系统行为；
- 每条只保留一个主要结论；
- 两条高度相似时，保留责任更清楚、证据更强或岗位更相关的一条；
- 验证通常并入对应设计，只有跨多条链路的独立质量体系才单独占一条；
- 删除任意一条后若没有损失独立岗位信号，这条不应保留。

停止条件：

> 下一条 bullet 不再增加新的岗位信号、核心行为、失败边界、工程判断、验证闭环或独立面试故事时停止。

每个项目可写 1–5 条，没有三条下限。不能为了数量拆分机制、重复价值、抬高外围功能或补造数字。

## 7. 语言强度

- 使用“负责、设计、实现、重构、优化、定位、验证”等明确动作；
- “主导、牵头、上线、支撑、提升”需要对应个人归属或效果来源；
- 避免“全面、极致、企业级、工业级、海量、高可用、显著、大幅”等无边界营销词；
- 先写可观察行为，再写必要模块名；一条内最多保留少量通用技术术语。

## 8. 技术栈

只保留满足以下至少一项的技术：直接参与核心链路、是岗位筛选信号、在 bullet 中有对应设计、候选人能够回答原理和失败边界。

删除只在依赖文件出现的技术、与岗位无关的工具清单、候选人答不住的深水区和同义框架堆叠。

## 9. 完成标准

- 项目标题让非项目成员理解对象和边界；
- 项目描述包含场景、链路、边界和职责，但不堆机制；
- 最终 1–5 条 bullet 各自证明不同能力，数量由新增信号决定；
- 每条可以还原为场景、失败、动作、边界和验证；
- 没有真实业务时使用任务场景，没有虚构用户和影响；
- 技术栈中的每个词都能在正文或面试中解释。
